## 1. 架构选择（含被否方案及理由）

### 1.1 选定：单包 Python CLI（`mpdt`），stdlib 优先 + requests 唯一第三方依赖

```
mpdt/
├── cli.py            # argparse 子命令 init/fetch/report；退出码路由 0/2/3/4
├── config.py         # ~/.mpdt/config + .env 读写（chmod 600）
├── session.py        # 凭据装载、token/fingerprint 自动刷新（页面 URL 正则）、限速器（≥1s）
├── fetchers/
│   ├── publish_list.py    # appmsgpublish 端点（双重 JSON 解码，独立封装）
│   ├── article_channel.py # 单篇渠道页：完读率/推荐/搜一搜占比/分享在看收藏
│   └── datacube.py        # datacube 用户/图文表（T+1 口径、7 天窗口约束）
├── store.py          # SQLite 快照（(日期,文章id) 幂等 upsert）+ CSV 导出 + 运行日志表
├── report.py         # Markdown（默认）+ HTML 周报：周环比/完读率 Top10/渠道结构/口径说明
└── templates/        # P1 模板包挂载点（FR7 预留，配置注入切换）
```

**决策依据**：①通道已被 mp-datacube.py 真实打通（fetchers 三模块=把已验证代码产品化，非新研发）；②SQLite/argparse/string.Template 全 stdlib，依赖面最小=用户安装摩擦最小（P-A 画像转化关键）；③微信端点变更只改对应 fetcher 单文件（NFR 可维护性）。

### 1.2 被否方案

| 方案 | 否决理由 |
|---|---|
| 官方 API Only（api.weixin.qq.com） | 拿不到完读率/推荐占比/搜一搜占比——核心价值指标只在后台 UI 端点（01-req E7：连开源作者都答「不能」）。致命功能缺口 |
| Selenium/Playwright 浏览器自动化 | 重依赖+脆弱（选择器随改版碎）+资源占用违反克制边界；直连 HTTP+复用登录态已被自家验证等价可行 |
| 托管 SaaS | 费用（>50 元请示边界）+ToS 灰色放大+「数据不出本机」卖点自相矛盾（PRD OoS#2） |
| 浏览器插件 | 撞壹伴主赛道+商店审核+形态重（PRD OoS#5） |

## 2. 数据流

```
用户浏览器登录态（手工复制，一次性）
  → session.py（token 自动刷新；失败=退出码 3+指引）
  → fetchers 三路拉取（限速 ≥1s，白名单 mp.weixin.qq.com）
  → 归一化记录（统一 schema：日期/文章id/指标/口径标签）
  → store.py SQLite 快照（幂等 upsert + 每次运行留 journal 行）
  → report.py 读快照 → weekly-YYYY-Www.md/.html（文首口径说明）
```

回填：`fetch --backfill N` 逐日拉取（datacube 7 天窗口内），历史更早数据只能靠快照积累（README 明示——这是诚实边界，不做超窗口的假回填）。

## 3. 外部依赖（API/凭据/成本）

| 依赖 | 性质 | 成本 | 可替代性 |
|---|---|---|---|
| mp.weixin.qq.com 后台 UI 端点（appmsgpublish/单篇渠道页/datacubequery） | 未公开文档、随时可能变 | 0 元 | **不可替代**（完读率等指标唯一来源）→ 已按「单点不可替代依赖」标注，缓解见风险 R1 |

**成本核查（P14）：全部 0 元，无请示项。** ✅ 质量门达标。

## 4. 风险清单（每项带缓解）

| # | 风险 | 概率/影响 | 缓解 |
|---|---|---|---|
| R1 | 微信改版致端点/结构变更（单点依赖） | 中/高 | FR6 错误语义：退出码 4+「上游接口异常」+原始返回片段→用户可一键反馈；fetcher 单文件隔离改一处即修；快照数据不丢（历史已留存） |
| R2 | 自动化访问后台的 ToS 灰色/账号风险 | 低/高 | 只读+人用级频率（≥1s 间隔）+不模拟发布+工具内免责声明；**验证期（V1）完全不分发工具**，只发教程+留资——正式分发前用户终审 |
| R3 | token/fingerprint 过期打断体验 | 高/中 | FR2 自动刷新（URL 正则方案已验证）+失败指引文案（AC3）；文档给「刷新失败 90 秒自救」路径 |
| R4 | 数据口径误读（T+1/送达口径/7 天窗口） | 中/中 | 每份报告文首口径说明；AC4 强制 T+1 提示；README 口径表 |
| R5 | 开源核心被白嫖、付费层卖不动 | 中/中 | 付费层=模板包+进阶功能（时间价值型），核心开源是信任基建（H2）；P14 保守预期已按 50 用户计，不依赖右尾 |

## 5. MVP 范围划定

**MVP = PRD P0 全部（FR1-FR6）且仅 P0**。两周交付最小闭环：init→fetch→快照→report 一条链 + 错误语义。P1（FR7-9）在 V1 验证通过且 MVP 自用 ≥2 周后启动。✅ ≤ P0，质量门达标。

## 6. 回滚设计

全本地、零外部状态：①代码走 git，每功能点一 commit+tag，坏版本 `git revert` 即回；②快照 DB 只追加（journal 表记录每次运行），错误运行可按 journal 定位并重跑覆盖；③配置/.env 永不被程序自动改写（只在 init 显式创建）；④分发后若发现严重问题：仓库下架 release+公告，用户本地数据完整保留——**不存在不可回滚路径**。

## 7. 阶段 3 · 三角色评审（同文档合并）

### 7.1 工程师视角
- 端点脆弱性是结构性的（R1）——但缓解设计合理：错误分类学+模块隔离+快照解耦，改版修复成本被压到单文件。**WARN**：双重 JSON、fingerprint 机制这类奇技细节必须有单元测试锁定（用录制的真实返回做 fixture，防止回归）。
- requests 唯一依赖合理，但若追求零依赖可用 urllib——**NOTE**：不做，requests 已是事实标准，安装摩擦差异可忽略。
- 并发/多账号（P2）暂不入 MVP，schema 预留 account 字段。**NOTE**。

### 7.2 商人视角（P8）
- 单位经济：边际成本 0（纯本地），获客=内容营销（V1 技术文+壹伴式系列文打法），CAC≈时间。9.9-39 元一次性买断 × 保守 50 用户 = 495-1,950 元/年，盈亏平衡点=0（无固定成本）。**数字成立但量级小**——符合 P14 预期管理：这是验证型产品，不是收入主力；真正价值=逆向能力的产品化证明（Process Power 积累）。
- **WARN**：定价与付费形态在 V1 留资时应用价格锚点测试（「9.9 元级」口径已埋），阶段 6 再定档；勿在验证前过度开发。
- **BLOCKER 候选→降级 WARN**：「开源核心+付费增值」的边界（哪些进开源哪些收费）未定——不阻塞开工（MVP 全开源自用），在 FR7 模板包设计时定。

### 7.3 挑剔用户视角
- 「为什么不用壹伴？」：99 元/月 vs 一次性几十元、不绑账号、数据不出本机（H2 偏好）——答案清晰，V1 文案直接打此差异。✅
- **WARN（转化关键）**：init 引导质量决定生死——P-A 虽技术型但耐心有限，目标「复制 cookie→跑通首份周报」≤10 分钟、≤3 步文档。AC3 的指引文案要按真实新手走查（P3：找真实用户走一遍，自家 dogfood 不算数）。
- 「数据真不出本机？」：开源代码+网络白名单可自查——信任证明链成立，README 需给出一行验证命令（如 `grep -r http` 式自查）。**NOTE**。

### 7.4 问题分级汇总
- **BLOCKER：0 → 过门** ✅
- WARN：①端点 fixture 测试锁定奇技细节；②付费边界 V1 后定；③init 新手走查；④（合并自商人节）价格锚点进 V1 留资问卷。
- NOTE：urllib 后备、account 字段预留、README 自查命令。
